# RCA — RunningCoach (run-together-28): "Created trainings don't show up in the deployed app"

## TL;DR
The production app is **NOT** losing data. It is bound to a **persistent, Emergent-managed production MongoDB (Atlas)**, and that DB currently holds **6 training documents** plus **4 users** — all intact, none reset by inactivity. The real cause of the symptom is the **preview (Dev) environment and the deployed (production) environment use two completely SEPARATE databases**. Trainings created on the preview URL do not appear on the deployed URL, and vice versa.

---

## Evidence (production-side, verified)

**Deployment:** `run-together-28` · active run `d8459dd8-fdd6-48b2-a3b5-36b27865b608` (redeploy, status success) · live URL **https://run-together-28.emergent.host** · template `fastapi_vite_shadcn_base_image`, frontend served from Kubernetes.

**1. Production DB is real, bound, and persistent**
- `MONGO_URL` and `DB_NAME` secrets are present and non-empty on the active production run.
- Resolved production database name: **`run-together-28-test_database`** (this is the Emergent-managed Atlas prod DB — note the prod DB name intentionally differs from the preview DB name; the `test_database` suffix is just the stored DB_NAME value, it is the production database the live app reads/writes).
- Collections present: `users`, `trainings`.
- `trainings` count = **6**; `users` count = **4**.
- Sample documents confirm real, persisted data (e.g. "Ranný beh v parku", "Intervalový tréning", "Dlhý nedeľný beh", "UI Test Beh …"), with `created_at` timestamps from 2026-09-30 still present now. No TTL index, no scheduled cleanup, no reset-after-inactivity behavior. **Data persists.**

**2. Preview vs Production are SEPARATE databases**
- Preview/Dev runs against a **local MongoDB inside the agent-env (preview) pod**. Production runs against the **Emergent-managed Atlas** DB `run-together-28-test_database`. They are unconnected.
- Consequence: a training you create on the **preview URL** is written only to the preview DB and will **never** appear on **https://run-together-28.emergent.host**, and vice versa. This is the most likely explanation for "created trainings don't show in the final app."
- The "after inactivity" detail fits this too: the **preview pod sleeps after inactivity** and its local preview Mongo can lose/reset state across pod restarts. **Production Atlas does not** — so if data seems to vanish after inactivity, that is the *preview* side, not production.

**3. Production DB persists across redeploys**
- Redeploys push a new code image but do **NOT** wipe production data. A Mongo data copy only happens on an explicit fresh-DB / mongo-migration trigger.
- Proof: the deployment went through an initial deploy and then a code redeploy, and the 6 trainings created back on 2026-09-30 are still present on the current active run. Pre-existing production data survived the redeploy.

**4. Admin access in production is already set up**
- `ADMIN_EMAILS` secret is present, non-empty, and its value **matches `matusko.lunter@gmail.com`** (verified via matches_expected). So the user can create/manage trainings directly on the live production URL with that admin email.

## What the user must do

- **To populate production:** create trainings while logged in (admin `matusko.lunter@gmail.com`) on the **live URL https://run-together-28.emergent.host** — NOT on the preview URL. They will persist in production and survive redeploys and inactivity.
- **To move existing preview trainings into production:** use **Deployment Panel → Database (DB Manager)** to copy entries from preview → production. (Preview data cannot otherwise reach prod.)
- **Unpushed preview code changes:** code changed in preview since the last deploy is NOT live yet. If the user wants those changes in production, **redeploy** from the Deployment Panel. (This does not affect existing production data.)

## What is NOT the problem
- Production is not connected to the Dev database. It has its own persistent Atlas DB.
- There is no data loss / no inactivity-based reset on the production side.
